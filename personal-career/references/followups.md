# Progress and follow-ups

Run only when asked. Read the existing Notion tracker, confirmed events and current direct-user corrections; preserve the difference between current Stage and historical legacy Status. Do not schedule background checks.

Use `support` and `actions` to prepare a compact action list: application, effective stage, last confirmed event/contact, outstanding question, recommended action and any suggested timing. Deferred rejection corrections suppress active follow-ups locally. Applied/Interview/On Hold must come from real evidence, not the presence of a CV or draft.

For each actionable process, draft a brief message anchored to the actual conversation and employer's stated timing. If dates or promised response times are unknown, state that and propose timing rather than inventing an elapsed wait. Reuse relevant upstream `modes/followup.md` content as writing guidance only.

Drafting does not send. Save a proposed date/status only when the user explicitly chooses it or confirms an actual event. `event-check` requires a user-confirmation reference and preserves null dates. Then use the minimal Notion patch protocol. User-submitted applications can be marked Applied after confirmation; a prepared CV stays Preparing. A sent follow-up must be confirmed independently of its draft.

Present pending verification items such as sponsorship and base pay alongside actions. Keep old interviewers, historical scores and closed processes out of active recommendations unless the user asks for a retrospective.
